A 的 3 张图和 B 的 6 张图怎么组织

| 层级 | jME3 建议 |
| --- | --- |
| VT 服务 | 每个渲染设备或上下文统一管理资产注册、请求去重、I/O、预算和淘汰。主视口、预览视口、捕获视口可以提交各自的需求。 |
| 虚拟纹理资产 | 每张可独立复用的原图可有自己的 VT 资产和 mip 页索引。SDK 另可把经常一起使用的多张图生成为一个多层派生资产。 |
| 材质采样 Stack | 根据实际采样坐标和页布局分组。对齐的图层共用一次请求地址计算，页项可以记录各层的物理位置。第一版可以让同组各层同时驻留。 |
| 物理页池 | 按兼容的 GPU 存储格式、色彩空间、物理页尺寸及边框分池。来自不同材质、不同原图尺寸的页可以共享同一兼容池。颜色、法线和其他数据各自保留采样语义。 |

A 的 1/2/3 假设是同为 4K 的 diffuse、normal、specular，使用同一套 UV、变换、寻址、mip 策略和页网格，就组成 Stack A。某个片元只需发出 (stackA, mip, pageX, pageY)。运行时由这一条请求得到三个图层的页，着色时分别读取三层。比如 diffuse 在 sRGB 池，normal 在 BC5 线性池，specular 在适合它的线性池。共用一个虚拟页地址，物理位置可以不同。 若三层采用同步驻留，就等三层都上传后再发布该页映射，避免同一位置的颜色和法线分批跳清晰度。

B 的 7–12 可以这样处理。假设 7/8/9 是同一 UV 的 8K 材质主贴图，组成 Stack B0。10 是同一 UV 的 2K mask，可直接用普通 sampler，确实需要流送时再作为独立 VT。11/12 如果使用另一套 UV 或不同平铺比例，就按它们自己的采样关系建 B1，必要时各自独立。A 和 B 无须统一分辨率。若 8K 图和 2K 图以后确实值得合栈，可以增加显式的相对 mip 映射。同一 UV 足迹下，两者所需 mip 编号相差约两级，仍须验证页网格、边界及过滤契约。首版保持原分辨率，采用对齐才合栈的规则。若同一张图被 A、B 复用，底层用原图资产和页坐标去重，避免按材质保存两份。

一个屏幕像素怎么反馈多个页

屏幕像素是采样反馈的位置。请求地址来自那个片元实际使用的 UV、UV 导数、纹理尺寸和 Stack。一个片元采样 A0 一次，只需要一条组请求。一个片元采样 B0 和 B1，就可能产生两条不同的请求。

旧版 [VTFeedbackPass.frag](D:/MyWorks/Jme3/Sources/VirtualTexture-master/assets/Shaders/VTFeedbackPass.frag) 和 [VirtualTextureCache.java (line 190)](D:/MyWorks/Jme3/Sources/VirtualTexture-master/src/mygame/vt/VirtualTextureCache.java:190) 只定义了一个 RGBA8 记录，分别装反向 mip、X、Y、纹理 ID，因此每次只能写一条，ID 和坐标也各只有 8 位。接入时建议这样做：

- 首版验证用低分辨率反馈 Pass，输出整数页 ID。一个 Stack 写一条。需要同时覆盖两个独立 Stack 时，可用有限的整数附件，或跨帧轮换反馈组。轮换会增加请求延迟，需要固定粗 mip 兜底。
- 正式桌面路径让 Forward 和 GBuffer 的 VT 采样向有界 GPU 请求缓冲发出多条记录，按视口稀疏采样，再去重、压缩和异步回读。这样无需按贴图槽重画六遍。去重只减回读量，原子写入与过度绘制仍需测量。请求应包含想要的 mip，并让缓存知道本次实际命中的父页仍在使用。低分辨率反馈也要按实际渲染尺寸校正导数和 mip。

UE4.27 的 Streaming Virtual Texturing 与这个方向一致。 原图可独立启用 VT，材质使用 Virtual Sampler。Epic 将开销拆成各贴图自己的数据 lookup，以及使用相同 UV 和 Sampler Source 时可合并的 Stack lookup。现代 UE 的公开 API 还明确区分每层对应的 producer 和 producer layer，物理池则按格式及 tile 尺寸配置。这个例子支持借鉴“资产、采样 Stack、物理池”的分层。首版的同步驻留和合栈规则是针对 jME3 的设计选择。Unity 的 SVT 也把同时采样且共享 UV 的纹理定义为 Texture Stack。 Epic UE4.27 SVT · Epic VT 分配描述 · Epic 物理页池 · Unity SVT

引擎和 FrameGraph 要改什么

普通纹理还是 VT是一项选择，绑定 sampler 还是 Bindless是另一项。现有 [Material (line 899)](D:/MyWorks/Jme3/Sources/jmonkeyengine/jme3-core/src/main/java/com/jme3/material/Material.java:899) 已有 Bindless 请求和普通 shader 路径。建议先交付 普通纹理 + 绑定、`普通纹理 + Bindless`、`VT + 绑定`。以后按实测决定是否加 VT + Bindless，因为多个材质已经能共享少量页池，边际收益要单独测。模式切换在帧边界生效，保留原 TextureKey。切回普通模式时先使普通纹理可用，再停止 VT 工作并安全回收资源。显存紧张或刚切换时可以先用较低分辨率的普通变体，避免两套全量资源重叠。

按当前 [RenderManager (line 1883)](D:/MyWorks/Jme3/Sources/jmonkeyengine/jme3-core/src/main/java/com/jme3/renderer/RenderManager.java:1883) 的顺序，建议增加这些阶段：

| 阶段 | 放置与职责 |
| --- | --- |
| VT Upload / Publish | 帧初、任何会采样 VT 的 Pass 之前。非阻塞收割旧反馈及已读完的页，按字节预算做局部上传，再发布页表。若阴影的 Alpha Test 也读 VT，要放在 ManagedShadows 之前。旧映射先失效，槽位在先前读取安全结束后才能复用。 |
| VT Feedback | 第一版在 SceneQueue 后、队列消费前单独绘制，复用实际视口的投影和材质 UV。正式版并入 Forward opaque、Deferred GBuffer 和实际会采样 VT 的 forward fallback。这样反馈跟随实际材质及可见性。透明和 Alpha Test 要按它们各自的绘制语义接入。 |
| VT Compact / Readback | 在最后一个反馈写入者之后去重、限流并提交异步回读。Compute 路径可以复用现有 [`Renderer.requestBufferReadback` (line 730)](D:/MyWorks/Jme3/Sources/jmonkeyengine/jme3-core/src/main/java/com/jme3/renderer/Renderer.java:730)。低分辨率纹理反馈需要对应的 PBO 和 fence 路径。磁盘 I/O 由 worker 承担。 Khronos Pixel Readback |

SDK 首版需要资产转换、材质绑定和预览。 可在现有 Texture Tools 增加 VT 派生资产生成，输出版本化索引、页数据、原始 key、色彩空间、mip 和边框信息。材质编辑器按纹理槽选择 VT 和 Stack，旧 J3M/J3O 继续解析原 key。Scene Composer 加模式切换和页池诊断，区分编辑器预览与项目运行设置。现有 [GeneratedTextures](D:/MyWorks/Jme3/Sources/jmesdk/jme3-texture-tools/src/com/jme3/gde/texturetools/GeneratedTextures.java) 可作为派生资产所有权和失效管理的接入点。路线图已经单列 LightProbe 烘焙，六面捕获应先预取并固定一批页，或明确全程使用固定粗 mip，避免烘焙结果随回读时机和面顺序变化。也应和表面卡片流送协调显存预算。 [渲染路线图](D:/MyWorks/Jme3/Sources/jmonkeyengine/RENDERING_QUALITY_ROADMAP.md)

旧实现的性能判断

从源码看，旧版的优势是按需读页、有限大小的物理缓存、父 mip 回退。主要风险是新增页时的帧时间尖峰，其次才是热缓存下的着色开销。优先级如下。

1. 先取消整图集上传。 uploadPageToVTCache() 在 CPU 上逐像素复制和翻转，再对整个 Image 调 setUpdateNeeded()。`Main` 的配置是 (256 + 2) × 12 = 3096 像素见方，ABGR8 图集约 36.6 MiB，单页约 260 KiB。单页变化时，整图集的名义数据量是局部上传的 144 倍，CPU 也保留了整张图集的镜像。先用当前引擎的区域更新接口验证未压缩页，随后补压缩块或数组层更新。页表也更新脏区，文件中预先统一行方向。 [旧图集上传 (line 448)](D:/MyWorks/Jme3/Sources/VirtualTexture-master/src/mygame/vt/VirtualTextureCache.java:448) · [Renderer 区域更新 (line 472)](D:/MyWorks/Jme3/Sources/jmonkeyengine/jme3-core/src/main/java/com/jme3/renderer/Renderer.java:472)
2. 再移除同步反馈回读。 旧实现虽然轮换 feedback buffer，最终仍向 CPU ByteBuffer 调 readFrameBuffer()。低分辨率减小字节量，等待 GPU 完成相关绘制的可能性仍在。用异步回读环和零等待轮询，槽位未就绪就继续使用旧数据。GPU 去重之前，CPU 至少应按整个反馈批次做去重，旧版只跳过相邻重复项。 [旧反馈回读 (line 58)](D:/MyWorks/Jme3/Sources/VirtualTexture-master/src/mygame/misc/FeedbackData.java:58) · [旧反馈解析 (line 176)](D:/MyWorks/Jme3/Sources/VirtualTexture-master/src/mygame/vt/VirtualTextureCache.java:176) · OpenGL 同步说明
3. 把 I/O 和淘汰改成有预算的调度。 旧版逐 .page 文件读取，用字符串页键，待办与待淘汰页有整表排序，4 帧过期策略易受快速转向和 I/O 延迟影响。改用索引页包、整数页键、全批次去重和按覆盖率、可见时间、粗 mip 优先级调度。粗 mip 常驻，按字节限制上传，明确溢出时的 mip 偏置和重试。压缩页尽量直接上传，保留各图层的格式和色彩空间。 [旧文件读取 (line 40)](D:/MyWorks/Jme3/Sources/VirtualTexture-master/src/mygame/streaming/BaseTextureStreaming.java:40) · [旧淘汰逻辑 (line 281)](D:/MyWorks/Jme3/Sources/VirtualTexture-master/src/mygame/vt/VirtualTextureCache.java:281)
4. 最后调画质与采样成本。 旧版页池只开 bilinear、无物理 mip，示例边框是 1 texel。多层 PBR 要重新验证接缝、斜视角各向异性、跨 mip 过渡，以及 normal mip 的正确过滤。用 64、128、256 页做同画质比较。大页减少请求数量，小页降低读入不可见 texel 的浪费。合栈能节省地址计算与页表访问，同步驻留也会扩大每个请求的字节数。 [旧图集配置 (line 91)](D:/MyWorks/Jme3/Sources/VirtualTexture-master/src/mygame/vt/VirtualTextureCache.java:91) · [旧采样库 (line 21)](D:/MyWorks/Jme3/Sources/VirtualTexture-master/assets/Shaders/VTCommon.glsllib:21)

我的建议是先用旧地面样例加上 A/B 双材质场景，验证局部上传、异步反馈、共用页地址和三种运行模式，再做四条渲染路径与 SDK 验收。测试要同时看静止热缓存、冷启动、快速转向和页池超预算，记录 CPU/GPU 帧时间 P95/P99、上传字节、缺页率、回退 mip 和从请求到清晰的时间。预期收益是让超大纹理的显存工作集可控，降低流送峰值。稳态 FPS 是否提升要实测，常驻普通纹理能装进显存的小场景，VT 的间接采样和反馈本身就有额外成本。本次未运行样例或测帧。

## SDK 生成与原路径映射

**用户**

然后使用上应该如何设计？VT是对纹理右键启用VT，然后在j3m里手动赋值VT图吗？ue4是不是这样设计的？那么如果我不希望赋VT图，而是希望j3m里的纹理槽位还是旧的图的路径，然后只要右键纹理（可以多选）或右键某个j3o（自动遍历里面的j3m关联的纹理）就能选择“生成VT”的操作，这种设计合理吗？

**助手**

合理，我建议 jME3 就用这个工作流。 J3M 和 J3O 里的纹理槽继续保存现有 TextureKey。在 SDK 里右键一张或多张纹理，或者右键 J3O，执行 生成 VT。工具生成分页数据和映射清单。运行时开启 VT 后，支持 VT 的材质槽自动按原 key 找到分页版本。你平时仍像现在一样给材质拖贴图。

UE4.27 怎么做

UE4.27 在 Content Browser 提供 Convert to Virtual Texture，支持选择纹理后批量转换。确认窗口会列出选中的纹理和引用它们的材质。确认后，编辑器在现有 Texture Asset 上启用 Virtual Texture Streaming，同时把引用材质的采样节点改成 Virtual Sampler。因此，走右键转换时，用户通常无需逐个重新赋图。如果只在 Texture Editor 手动打开 VT 开关，则需要修正引用材质的采样器类型。 UE4.27 Streaming Virtual Texturing

jME3 可以保留类似的批量体验，同时利用现有的资产映射模式。UE4 转换会编辑引用材质的采样节点。jME3 可以由支持 VT 的 .j3md 根据运行时解析结果选择 shader 变体，J3M 无需新增 VT 纹理槽。 引擎和内置材质定义需要为支持的槽声明 VT 采样能力。已有自定义材质可以继续走普通 sampler，逐个接入 VT。

我建议把生成粒度设为单个纹理变体，Stack 由材质运行时决定。右键 A.j3o 可以一次生成 1/2/3，右键 B.j3o 可以一次生成 7–12。即使用户以后替换 A 的其中一张图，也只需生成新图的派生数据。材质发现几张 VT 的 UV、采样方式及页网格兼容时再合栈。这也让同一张贴图可以被多个 J3O 共享。

原路径如何解析到 VT

例如 J3M 的 BaseColorMap 仍指向 Textures/Wall/brick.png。项目清单记录这个逻辑 key 对应哪份 VT 页包、源图指纹和生成参数。同一路径若确实同时被当作 sRGB 颜色和线性数据使用，可以有两个变体，由材质槽的采样语义决定匹配哪一个。

运行时应在支持 VT 的材质槽解析阶段选择数据。项目或视口启用了 VT、槽位支持、设备满足要求、且存在有效产物时，才使用 VT。其他情况沿该 key 走现有普通纹理路径，包括已有的 DDS 映射。这个位置也很重要：决定走 VT 后，应允许直接加载 VT 描述和粗 mip，避免资产系统先把整张原图解码或上传一遍。

SDK 现有 GeneratedTextures 已经有 DDS 所有权、逻辑路径映射及缺失或过期重建的基础。VT 可以沿用这套管理思路。对旧 J3O 中直接保存的 .dds key，有登记的原图时优先由原图生成，并登记旧 key 的映射。只有 DDS 时，明确标记源为 DDS。独立游戏打包时也要带上运行时清单和页包，这样同一个 J3O 在 SDK 外也能解析。 [SDK GeneratedTextures (line 18)](D:/MyWorks/Jme3/Sources/jmesdk/jme3-texture-tools/src/com/jme3/gde/texturetools/GeneratedTextures.java:18)

还有一个交互细节值得定下来。“生成 VT”以资产为单位，是否使用以项目、视口或材质为单位。 右键某个 J3O 是批量收集资产的入口。两份 J3O 如果共用同一张图，生成一次后，在开启 VT 的预览里两份都可以命中。这样菜单语义清楚，也能随时关闭 VT 比较原画面，无需重新保存材质。

## 不同尺寸贴图的反馈

> A 的 1/2/3 假设是同为 4K 的 diffuse、normal、specular，使用同一套 UV、变换、寻址、mip 策略和页网格，就组成 Stack A。

**用户**

但是通常1/2/3不会尺寸一致，这种情况下没法用一个屏幕坐标一次feedback到三个虚拟page吧？该怎么处理这种？

**助手**

同一个屏幕采样点可以反馈三张不同尺寸的贴图。 首版建议在同一次片元着色里，按每张贴图的尺寸分别算出 (纹理 ID, mip, pageX, pageY)，把三条请求写进同一个反馈缓冲，再统一去重和异步回读。一次屏幕采样就够，也只需要一套反馈流程。旧版的限制来自 每个像素只有一个 RGBA8 记录槽。

尺寸不同，有时也能共用一条反馈

假设 diffuse 是 4096²、normal 是 2048²、specular 是 1024²，三者用相同 UV，页大小都是 128。某个片元的 UV 足迹可能让它们分别请求：

| 纹理 | 请求 mip | 该 mip 的尺寸 | 页网格 |
| --- | --- | --- | --- |
| Diffuse | 3 | 512² | 4 × 4 |
| Normal | 2 | 512² | 4 × 4 |
| Specular | 1 | 512² | 4 × 4 |

这里三张图原始尺寸不同，但所请求的 mip 恰好有相同的页网格。此时可以只发一条 Stack 请求，由运行时用各层的 mip 偏移展开成三个独立页。前提是 UV 变换、寻址、LOD 规则和页边界都对齐。

但镜头拉近时，情况可能变成 diffuse 请求 mip 1、normal 请求 mip 0、specular 也只能请求 mip 0。这时 diffuse 和 normal 的 mip 都是 2048²，specular 仍是 1024²，页网格就分开了。不能把同一组 pageX/pageY 直接套给三张图。 如果有不同的 UV 平铺、独立 mip bias 或长宽比，分开的情况会更多。

我建议 jME3 这样做

- 资产仍按原尺寸分别生成。 4K diffuse、2K normal、1K specular 各自分页，保留 J3M 原路径。小图是否使用 VT 可以独立决定。
- 首版以逐图反馈保证正确。 同一个片元、同一套 UV 可以复用导数，但每张图按自己的尺寸和采样规则计算请求。反馈缓冲支持一对多，去重后只把有效请求交给流送器。
- 后续再按实际页网格合并。 能证明页地址对齐的层共享一条反馈，其他层发独立记录。若合并需要复杂的分支或让图层多读很多页，就保持独立。即使合并反馈，各图层仍可独立驻留和淘汰。

所以，前面提到的「三张都 4K」只是最简单的共享页地址示例。实际使用中，你可以照常搭配 4K、2K、1K 贴图。不同尺寸由引擎自动处理，共享反馈是可选优化。

## Stack 的含义

> Stack

**用户**

Stack是啥意思？

**助手**

这里的 Stack（虚拟纹理采样组），就是把材质里几张能共用一次页地址查询的贴图编成一组。

比如一个墙面材质同时采样颜色图和法线图。两张图使用同一套 UV，而且当前所需的 mip 页网格对得上，那么 shader 可以查一次页表，拿到两张图各自的物理页位置，再分别采样颜色和法线。这种情况下，反馈也可以发一条组请求，让流送系统找出两张图各自需要的页。

在我们讨论的 jME3 方案里，Stack 由材质采样逻辑自动决定。你照常在 J3M 里给颜色、法线等槽位赋原图路径。能共用页地址的槽位自动成组，页网格对不上的槽位就各自查表、各自反馈。

## 烘焙时的 VT 策略

> 路线图已经单列 LightProbe 烘焙，六面捕获应先预取并固定一批页，或明确全程使用固定粗 mip，避免烘焙结果随回读时机和面顺序变化。也应和表面卡片流送协调显存预算。

**用户**

烘焙时应该禁用VT吧，不然烘焙是不是会因为流送过慢而烘焙错误？

**助手**

对，建议 SDK 离线烘焙默认关闭捕获视口的 VT，使用普通纹理。 前面提到的「预取并锁定 VT 页」可以留给普通纹理的显存工作集装不下的超大场景。

VT 的反馈、读盘和上传跨帧执行。LightProbe 六面捕获时，第一面可能先采到粗 mip，后面几面才采到刚就绪的细 mip。颜色、法线、粗糙度和 Alpha Test 的差异都可能被写进烘焙结果。之后 VT 页再加载完成，也不会修正已经保存的 Probe 或 Lightmap。 这会让同一场景的烘焙结果受缓存状态和捕获顺序影响。

我建议把烘焙流程定成：

1. 仅对烘焙捕获强制使用普通纹理路径。 主视口可以继续用 VT。按原 TextureKey 解析常规纹理，允许沿用已有 DDS 映射。
2. 等本次捕获所需的普通纹理准备好，再开始写入结果。 使用正常 mip 过滤，并为整个六面或整批捕获固定纹理版本。遇到加载失败或超预算时，明确报告，避免把占位纹理写进烘焙资产。
3. 完成、取消或失败时释放烘焙资源。 超大场景若需要用 VT 烘焙，再提供显式选项，先为整批捕获预取并锁定目标 mip 页，确认驻留后才开始正式捕获。

这样实时预览享受 VT 流送，正式烘焙使用稳定、可重复的纹理输入。

## 超大场景分区烘焙

**用户**

如果场景非常庞大，是不是得分开烘焙？分区域？因为显存会爆炸

**助手**

是。超大场景应该按区域和批次烘焙，并按显存预算决定每批的大小。 上一条说的「烘焙关闭 VT」仍适合默认模式，但要限定为本批所需的普通纹理。如果把全场景的普通纹理一次性加载到显存，即使输出分区域保存，显存峰值也不会降下来。

分区要分清输入和输出

- 输出按区域分。 本批只烘焙该区域的 LightProbe 或静态 Lightmap 接收物体。一个 LightProbe 的六个面用同一批固定的资源，全部完成后再提交。Lightmap 优先按完整接收物体或图集分批，单个超大接收面再切块，并保留过滤边距。
- 输入按影响范围加载。 例如烘焙城镇东区，区外的山体、城墙或邻区灯光仍可能影响反射、遮挡和间接光。捕获应包含这些贡献者。近处按需加载细节，远处可使用固定 LOD、低分辨率纹理或代理几何。把场景边界当成烘焙裁切面，容易在相邻区域产生接缝。

我建议 jME3/SDK 按这个顺序做

1. 先做普通纹理的预算式分批。 每批估算纹理、网格、阴影、捕获目标、烘焙中间缓冲和 SDK 主视口的显存占用。准备齐本批资源，再开始捕获。完成后保存结果，释放下一批用不到的资源，共享资源继续复用。
2. 预算不足时先缩小批次，再降低远处输入成本。 少烘几个 Probe 或少安排几个 Lightmap 接收物体，能降低并发占用。如果单个 Probe 的六面捕获仍超预算，继续缩小批次数量也无济于事。这时要给它选择明确的远景 LOD 或纹理 mip，仍装不下再考虑 VT。
3. VT 烘焙作为超大场景的备用模式。 先为本批捕获收集目标页，按预算预取并固定，确认就绪后再正式烘焙。页集超预算时，明确缩小范围或选定更粗的目标 mip。六面捕获期间保持同一套驻留和质量策略，避免第一面模糊、后几面清晰。

现有区域 Lightmap 资产可以继续作为分区保存和重烘的单位。真正控制显存峰值，需要另外管理烘焙期间哪些输入和临时资源同时驻留。SDK 首版我会优先设计成「选区域或整场景 → 按预算自动分批 → 支持重烘单个区域」，同时让相邻区域使用一致的捕获距离、远景 LOD 和纹理质量。
